# TRGS Skill 完整执行流程

## 流程总览

```
Input（原始大纲文本）
  │
  ▼
Step 1: 输入解析
  │
  ▼
Step 2: Blueprint 构建（内含 Step 3 策略决策）
  │
  ▼
Step 3: 策略决策（已内嵌于 Step 2 第三步）
  │
  ▼
Step 4: 资源生成（并行）
  │         ├── 4a: PPT 生成
  │         └── 4b: 交互组件生成
  ▼
Step 5: 质量检查
  │
  ▼
Step 6: 交付
  │
  ▼
Output（最终文件集）
```

---

## Step 1: 输入解析

### 输入

- 原始大纲文本（1 份或多份）
- 格式不限：纯文本、Markdown、粘贴的表格内容均可

### 处理流程

1. 识别大纲边界：判断输入中包含几份独立大纲，按主题/标题层级切分
2. 提取原始结构：识别章节（Chapter）、小节（Section）、知识点（KnowledgePoint）的层级关系
3. 标准化字段：为每个节点生成唯一 ID，标注层级深度
4. 标记元信息：提取大纲标题、适用对象（如有）、总课时数（如有）

### 输出

- 解析后的大纲列表（Parsed Syllabus List），结构如下：

```json
[
  {
    "id": "syllabus-01",
    "title": "大纲标题",
    "chapters": [
      {
        "id": "ch-01",
        "title": "章节标题",
        "sections": [
          {
            "id": "sec-01",
            "title": "小节标题",
            "knowledgePoints": ["知识点1", "知识点2"]
          }
        ]
      }
    ]
  }
]
```

### 错误处理

| 异常情况 | 处理方式 |
|---------|---------|
| 输入为空 | 立即中止，向用户请求提供大纲内容 |
| 输入无法识别为大纲结构（无层级、无章节划分） | 向用户确认：是否为大纲？请补充结构化信息 |
| 多份大纲存在冲突（同一知识点归属不同章节） | 列出冲突项，请用户裁决 |

---

## Step 2: Blueprint 构建

### 输入

- Step 1 输出的解析后大纲列表
- 可选约束条件：
  - `audience`：目标受众（如"初中二年级学生"）
  - `duration`：总时长或单课时时长（如"每课时 45 分钟"）
  - `style`：教学风格偏好（如"探究式""讲授为主"）

### 处理流程

执行 `prompts/blueprint-builder.md`，依次完成以下五个阶段：

1. **结构解析（Parse Structure）**
   - 将解析后的大纲映射为 Blueprint 的 Chapter → Section → KnowledgePoint 三级结构
   - 为每个 KnowledgePoint 分配唯一标识符

2. **知识点分析（Analyze Knowledge Points）**
   - 对每个知识点进行属性标注：
     - `difficulty`：难度等级（1-5）
     - `type`：知识类型（概念/技能/原理/应用）
     - `prerequisites`：前置依赖
     - `estimatedMinutes`：预估教学时长

3. **策略决策（Strategy Decisions）**
   - 调用 Step 3 策略引擎，为每个知识点确定教学形式
   - 详见下方 Step 3 说明

4. **资源规划（Resource Planning）**
   - 根据策略决策结果，规划每个 Chapter 需要生成的资源：
     - PPT 幻灯片（每章必选）
     - 交互组件（根据策略决策按需生成）
   - 生成 ResourceRef 列表，标注类型、关联知识点、预期交互形式

5. **校验（Validation）**
   - 对照 `schemas/blueprint-schema.json` 进行结构校验
   - 检查约束满足情况：
     - 每课时高复杂度交互不超过 2 个
     - 教学形式多样性（避免全部为同一类型）
     - 渐进原则（难度递进合理）
     - 时长总和不超过约束上限

### 输出

- `blueprint.json`，严格符合 `schemas/blueprint-schema.json` 定义

### 错误处理

| 异常情况 | 处理方式 |
|---------|---------|
| 校验失败（第 1 次） | 以更严格约束重新执行一次 Blueprint 构建 |
| 校验失败（第 2 次） | 向用户报告具体校验错误，请求人工介入或调整约束 |
| 大纲结构过于模糊，无法合理推断知识点属性 | 向用户请求补充信息 |

## Step 3: 策略决策（已内嵌于 Step 2）

### 说明

策略引擎（Strategy Engine）在 Blueprint 构建的第 3 阶段被调用，不作为独立步骤执行。此处单独说明其逻辑以便理解。

### 输入

- 每个 KnowledgePoint 的属性集合：
  - `difficulty`（难度）
  - `type`（知识类型）
  - `prerequisites`（前置依赖）
  - 所在章节的上下文位置

### 处理流程

执行 `prompts/strategy-engine.md`，进行三维评估：

1. **维度一：复杂度适配**
   - 根据知识点难度和类型，评估适合的交互复杂度
   - 输出：复杂度等级（low / medium / high）

2. **维度二：形式选择**
   - 根据知识类型和教学目标，选择最佳呈现形式
   - 可选形式：Slide（纯讲解）、Interactive（交互组件）、Mixed（混合）
   - 输出：推荐教学形式 + 具体交互类型（如拖拽、模拟、问答、可视化等）

3. **维度三：渐进编排**
   - 考虑知识点在课程中的位置，确保难度渐进
   - 避免连续高复杂度交互造成认知过载
   - 输出：最终策略决策（可能调整维度二的推荐）

### 输出

- 每个 KnowledgePoint 的 `strategy` 字段被填充，包含：
  - `form`：教学形式
  - `interactiveType`：交互类型（如适用）
  - `complexity`：复杂度等级
  - `alternativeForm`：降级备选形式
  - `rationale`：决策理由

### 约束条件

- **复杂度预算**：每课时（Lesson）内高复杂度（high）交互最多 2 个
- **形式多样性**：同一课时内不得全部使用同一种交互类型
- **渐进原则**：课程前段以低/中复杂度为主，后段可逐步提升
- **时长约束**：所有交互组件预估时长总和不超过课时限制

---

## Step 4: 资源生成（并行）

### 输入

- 完整的 `blueprint.json`（已通过校验）

### 处理流程

对每个 Chapter 并行生成资源，包含两个子任务：

#### 4a: PPT 生成

- 执行 `prompts/ppt-generator.md`
- 基于 `templates/ppt-base.html` 模板
- 每个 Chapter 生成一个 HTML PPT 文件（`slides.html`）
- 生成要求：
  - 覆盖该章节所有知识点
  - 遵循策略决策中的形式标注
  - 幻灯片数量与知识点数量和时长匹配
  - 视觉风格统一，排版规范

#### 4b: 交互组件生成

- 执行 `prompts/interactive-generator.md`
- 基于 `templates/interactive-base.html` 模板
- 对每个 `type="interactive"` 的 ResourceRef 生成一个独立 HTML 文件
- 四阶段流程：

  1. **规格组装（Spec Assembly）**
     - 从 blueprint.json 提取该交互组件的完整规格
     - 包括：关联知识点、交互类型、复杂度、预期行为描述
     - 组装为生成器可消费的 Spec 对象

  2. **代码生成（Code Generation）**
     - 根据 Spec 生成完整 HTML 文件
     - 包含：结构（HTML）、样式（CSS）、逻辑（JavaScript）
     - 必须为单文件、自包含、无外部依赖

  3. **校验（Validation）**
     - 对生成的代码进行即时校验
     - 检查项：HTML 结构完整性、JS 语法正确性、交互逻辑闭环
     - 通过则进入下一步；未通过则进入自修复

  4. **自修复（Self-Repair）**
     - 根据校验反馈定位问题
     - 修复后重新校验
     - 最多执行 2 轮自修复

### 输出

- HTML 文件集合：
  - 每个 Chapter 一个 `slides.html`
  - 每个交互型 ResourceRef 一个 `interactive-XX.html`

### 并行策略

- 所有 Chapter 之间可完全并行生成
- 同一 Chapter 内，PPT 生成与交互组件生成可并行
- 同一 Chapter 内的多个交互组件之间可并行
- 并行度不受限制，根据实际资源情况调度

### 错误处理

| 异常情况 | 处理方式 |
|---------|---------|
| 单个交互组件生成失败 | 不阻塞其他资源，记录失败信息，进入 Step 5 的降级流程 |
| PPT 生成失败 | 重试 1 次；仍失败则简化内容后重试 |
| 模板文件缺失或损坏 | 中止该类型生成，向用户报告 |
| 单个 Chapter 全部资源失败 | 标记该 Chapter 为失败，继续处理其他 Chapter |

## Step 5: 质量检查

### 输入

- 所有已生成的 HTML 文件（PPT + 交互组件）

### 处理流程

执行 `prompts/quality-checker.md`，参照 `rules/generation-rules.md` 中的规则，进行三层检查：

#### 第一层：技术 QA（T1-T16）

适用于所有文件（PPT 和交互组件）：

- T1: HTML 结构完整性（DOCTYPE、html、head、body 标签齐全）
- T2: 无外部资源依赖（无 CDN 链接、无外部图片引用）
- T3: CSS 无语法错误
- T4: JavaScript 无语法错误
- T5: 无未定义变量引用
- T6: 事件监听器正确绑定
- T7: DOM 操作目标元素存在
- T8: 无无限循环风险
- T9: 响应式布局基本可用
- T10: 字符编码正确（UTF-8）
- T11: 无控制台报错
- T12: 文件体积在合理范围内
- T13: 无硬编码绝对路径
- T14: 图片/图标使用内联或 SVG
- T15: 无重复 ID
- T16: 语义化标签使用合理

#### 第二层：功能 QA（F1-F7）

仅适用于交互组件：

- F1: 核心交互功能可正常触发
- F2: 用户操作有即时视觉反馈
- F3: 正确/错误判定逻辑正确
- F4: 重置/重试功能可用
- F5: 边界输入处理（空输入、极端值）
- F6: 完成状态有明确提示
- F7: 多步骤交互的流程完整性

#### 第三层：教学 QA（P1-P11）

适用于所有文件：

- P1: 知识点覆盖完整（与 blueprint 一致）
- P2: 内容准确性（无知识性错误）
- P3: 难度与目标受众匹配
- P4: 表述清晰、无歧义
- P5: 视觉层次分明，重点突出
- P6: 信息密度适当（不过载、不空洞）
- P7: 教学逻辑连贯（有导入、展开、总结）
- P8: 示例/类比恰当
- P9: 排版美观、对齐规范
- P10: 色彩搭配协调、对比度达标
- P11: 交互设计符合教学目标（非为交互而交互）

#### PPT 简化检查

PPT 文件仅执行：
- 第一层完整检查（T1-T16）
- 第三层部分检查：P5、P6、P9、P10

### 输出

- 每个文件一份 QA Report，包含：
  - 文件名
  - 检查层级与项目
  - 每项结果（PASS / FAIL / WARNING）
  - FAIL 项的具体描述与定位
  - 总体判定（PASS / FAIL）

### 错误处理与降级链

```
QA FAIL
  │
  ▼
触发自修复（Self-Repair）：调用 `prompts/self-repair.md` 传入源码 + QA Report ── 最多 2 次
  │
  ├── 修复成功 → 重新 QA → PASS → 继续
  │
  ▼ （2 次修复后仍 FAIL）
降级为 alternativeForm（blueprint 中预设的备选形式）
  │
  ├── 降级成功 → 重新生成 → QA → PASS → 继续
  │
  ▼ （降级后仍 FAIL）
最终兜底：生成纯 Slide 版本
  │
  ▼
标记为降级输出，在交付时告知用户
```

---

## Step 6: 交付

### 输入

- 所有通过 QA 的文件（含降级输出的文件）
- QA Report 集合
- blueprint.json

### 处理流程

1. **文件组织**
   - 按章节创建目录结构
   - 将文件归入对应章节目录
   - 命名规范化：`slides.html`、`interactive-01.html`、`interactive-02.html`...

2. **生成导航页（可选）**
   - 生成 `index.html` 作为总入口
   - 包含：课程标题、章节目录、每个资源的链接
   - 标注降级资源（如有）

3. **生成 QA 报告汇总**
   - 输出 `qa-report.json`
   - 包含所有文件的检查结果摘要

4. **向用户报告**
   - 汇总信息：
     - 共生成 N 个章节
     - 共生成 M 个 PPT 文件
     - 共生成 K 个交互组件
     - 降级/失败项说明（如有）
   - 如有降级输出，明确告知用户哪些资源被降级及原因

### 输出

- 最终文件集（见下方"输出文件结构"）
- 用户可读的生成摘要

---

## 错误处理总则

1. **步骤独立性**：每个步骤拥有独立的错误处理逻辑，单步失败不导致全流程崩溃
2. **资源隔离性**：单个资源的生成失败不阻塞其他资源的生成
3. **最大重试次数**：每个资源最多重试 2 次
4. **最大降级次数**：每个资源最多降级 1 次
5. **最终兜底**：任何资源在穷尽所有手段后，至少产出一个纯 Slide 版本
6. **用户知情权**：所有降级输出必须在交付时明确告知用户，包括降级原因和影响的知识点

---

## 重试逻辑

| 场景 | 重试策略 |
|------|---------|
| Blueprint 校验失败 | 以更严格约束重试 1 次；仍失败则报告用户 |
| 交互组件生成失败 | 自修复 2 次 → 降级为 alternativeForm 1 次 → 兜底生成 Slide |
| PPT 生成失败 | 重试 1 次 → 简化内容后重试 1 次 → 报告用户 |
| QA 检查失败 | 在生成器自修复循环内处理（计入自修复次数） |
| 输入解析失败 | 不重试，直接请求用户澄清 |

### 重试计数规则

- 自修复次数从生成阶段开始计算，QA 阶段触发的修复共用同一计数器
- 降级后生成的新资源拥有独立的 2 次自修复机会
- 兜底 Slide 生成不设重试（使用最简模板，确保必定成功）

## 输出文件结构

```
output/
├── blueprint.json
├── index.html（可选，导航页）
├── chapter-01/
│   ├── slides.html
│   ├── interactive-01.html
│   └── interactive-02.html
├── chapter-02/
│   ├── slides.html
│   └── interactive-01.html
└── qa-report.json
```

### 文件命名规则

| 文件类型 | 命名格式 | 说明 |
|---------|---------|------|
| 蓝图文件 | `blueprint.json` | 固定名称，位于根目录 |
| 导航页 | `index.html` | 可选，位于根目录 |
| PPT 文件 | `slides.html` | 每章节一个，位于章节目录内 |
| 交互组件 | `interactive-XX.html` | XX 为两位数字序号，按生成顺序编号 |
| QA 报告 | `qa-report.json` | 固定名称，位于根目录 |

### 章节目录命名

- 格式：`chapter-XX`（XX 为两位数字序号）
- 按大纲中的章节顺序编号
- 从 01 开始递增
